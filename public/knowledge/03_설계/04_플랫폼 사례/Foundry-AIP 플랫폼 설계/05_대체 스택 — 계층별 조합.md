# ⑤ 대체 스택 — Foundry 없이 자체 설계 시 계층별 조합

> [!NOTE] TL;DR
> Foundry+AIP를 한 제품으로 대체하기는 어렵다. 자체 설계는 **계층별 조합**이다. 아래는 각 계층의 오픈소스/상용 후보.

---

## 계층별 후보

| 계층 | 역할 | 오픈소스 | 상용/클라우드 |
|------|------|----------|--------------|
| Storage/Lakehouse | 원천·정제 저장 | Iceberg, Delta Lake, Hudi, MinIO | S3, ADLS, GCS, Databricks, Snowflake, BigQuery |
| Ingestion | DB/SaaS/stream 수집 | Airbyte, Debezium, Kafka Connect, Meltano | Fivetran, Matillion, Confluent, AWS DMS |
| Transform | 정제·모델링 | dbt, Spark, Flink | Databricks Workflows, dbt Cloud, Dataform |
| Orchestration | 파이프라인 스케줄·의존성 실행 | Dagster, Airflow, Prefect | Astronomer, Dagster+, AWS MWAA |
| Catalog/Metadata | 검색·소유권·스키마·태그 | DataHub, OpenMetadata, Amundsen | Collibra, Alation, Atlan, Purview |
| Lineage | column/table/job lineage | OpenLineage, Marquez | Unity Catalog, Collibra, Purview |
| **Semantic/Ontology** | object/link/action 모델 | 직접구현, GraphQL schema, RDF/OWL, Neo4j, Hasura | Stardog, Neo4j EE, AtScale, Cube, **Foundry** |
| Authorization | RBAC/ABAC/ReBAC | OpenFGA, OPA, Cedar, Keycloak | Okta, Immuta, Privacera, AWS Verified Permissions |
| Feature/ML | feature store·registry·서빙 | Feast, MLflow, BentoML(서빙) | Databricks ML, SageMaker, Vertex AI |
| Vector/Retrieval | embedding·hybrid search | pgvector, Qdrant, Milvus, Weaviate, OpenSearch | Pinecone, Elastic, Vertex AI Search, Azure AI Search |
| LLM Gateway | routing·policy·logging | LiteLLM, vLLM | Azure OpenAI, Bedrock, Vertex AI, Mosaic AI |
| Agent/Orchestration | tool calling·workflow | LangGraph, Semantic Kernel, LlamaIndex, Haystack | LangGraph Platform, CrewAI Enterprise, Azure AI Foundry |
| Eval/Observability | eval·tracing·regression | Langfuse, Phoenix, Ragas, DeepEval, OpenTelemetry | LangSmith, Arize, WhyLabs, Datadog |
| Action/Workflow | 승인·작업 실행 | Temporal, Camunda, Windmill, n8n | ServiceNow, Jira, Salesforce Flow, Workato |

> [!WARNING] 채택 전 확인
> 라이선스·버전·성숙도는 빠르게 바뀐다. 특정 도구 채택 전 최신 상태를 직접 확인할 것. (이 표는 2026-07 시점 Claude·GPT 지식 + 일반 관례)
> **특히 Semantic/Ontology 행 주의**: GraphQL·Hasura·Cube·AtScale류는 object/link(조회 모델)까지만 대체한다 — **action·권한·감사까지 갖춘 온톨로지의 완전 대체는 사실상 직접구현**이고, 그 부분이 이 표에서 가장 비싼 공백이다.

## 도구 목록보다 중요한 것

> [!IMPORTANT] 자체 설계의 진짜 난이도는 "통합"에 있다
> 계층을 각각 좋은 도구로 채워도, **메타데이터와 권한 모델이 하나로 묶이지 않으면** Foundry형 가치가 안 나온다.
> - dbt lineage → **catalog**로 흐르고
> - catalog tag → **authorization policy**가 되고
> - authorization → **LLM retrieval + tool execution**에 일관되게 적용되어야 한다.

이 통합 실패가 [[06_안티패턴 — 흔한 실패 모드]]의 "카탈로그 따로, 권한 따로, 파이프라인 따로". 권한·거버넌스 설계는 [[03_보안·거버넌스 모델]] 참고.
