# Data·ML 기획 가이드

> Data·ML 기획은 데이터 가정, 평가 기준, 추론 계약과 운영 복구를 재현 가능한 형태로 확정하는 작업이다. ML 기능의 검수는 주관 인상이 아니라 **착수 전 발주사와 합의된 고정 평가셋·threshold**로만 판정한다.

## 책임과 경계

- 책임: ETL·ELT, 데이터 품질, feature, 학습·평가, 추론 interface, 모델 version·rollback
- 입력: 요구사항정의서(SRS)의 ML 요구·검수 기준, 데이터 source와 소유권(발주사 제공 데이터 포함), Database 계약, Backend 소비 방식, Privacy 요구
- 범위 밖: 일반 Backend API, UI, 평가 분할 없는 성능 단언, 실제 PII 평문 사용
- 다음 소비자: Backend, QA, DevOps·SRE, Security·Privacy, 발주사 검수자·운영자

## 기획 순서

1. [[01_데이터 계약·품질 규칙]]에서 source, schema, 분포와 결측 처리를 정한다.
2. [[02_라벨·분할·누수 방지]]에서 정답 정의와 독립 평가 경계를 만든다.
3. [[03_베이스라인·평가 계획]]에서 검수 metric과 비교 기준을 확정한다.
4. [[04_추론·모델 운영]]에서 입출력, 지연, version과 rollback을 정한다.
5. [[90_Data·ML 완료 체크리스트]]로 재현성·편향·운영 조건을 확인한다.
6. [[99_Data·ML Result Card 템플릿]]으로 실제 결과를 인계한다.

## 핵심 결정 원칙

- 데이터 schema·분포·결측 가정을 숨기지 않는다.
- 복잡한 모델 전에 단순 규칙이나 모델을 baseline으로 둔다.
- train / validation / test는 시간·사용자·그룹 누수를 막도록 분리한다.
- seed, 의존성, 데이터 snapshot과 feature 코드를 version으로 고정한다 — 검수 시 결과 재현이 안 되면 검수 근거가 아니다.
- 학습과 추론의 변환 경로를 동일하게 유지한다.
- PII는 목적에 필요한 최소 범위만 사용하고 익명화·해싱한다(발주사 데이터 사용 승인·범위 준수).
- 평가 기준·threshold는 **착수 전 발주사와 합의된 것만 유효** — 사후 합의는 분쟁 원인. 정확도 요구 상향 등 기준 변경 요청은 **CR(변경요청)로 회부**한다 ([[SI 수주와 범위 관리]]).

## 완료된 기획의 조건

- 고정 평가셋과 합의된 threshold가 있어 PASS / FAIL을 기계적으로 판정할 수 있다 ([[요구사항과 완료 조건]]).
- Backend가 입력·출력·오류·latency 한계를 합의했다.
- 편향, 데이터 누수, 낮은 신뢰도와 실패 시 fallback을 기록했다.
- 모델과 데이터 version으로 결과를 다시 만들고 되돌릴 수 있다 — 발주사 인수 후에도 재현 가능해야 한다.
- 종료 게이트: 다음 역할이 착수 가능한 동시에, 산출물이 **검수·계약 근거로 쓸 수 있는가**를 통과한다.
