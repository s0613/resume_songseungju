# Tech Lead·아키텍처 기획 가이드

> Tech Lead·아키텍트는 계약·요구사항정의서로 확정된 요구를 **기술 경계·계약·작업 소유권·통합·복구 계획**으로 바꿔 전문 구현자와 Reviewer에 인계한다. 산출물은 납품 문서와 직결된다 — 경계·구성 설계는 **시스템구성도**, API·데이터 계약은 **API정의서(인터페이스 정의서)·ERD·테이블정의서**로 제출되어 검수·인수인계의 근거가 된다 ([[외주 개발 산출물]]).

## 미션

- 시스템·도메인·신뢰 경계를 그려 변경 책임과 데이터 소유권을 명확히 한다 — 발주사 인프라·기존 시스템과의 경계 포함.
- API·데이터·NFR·실패 계약과 되돌리기 비싼 결정을 기록한다. 기술 결정(ADR)의 입력에는 **발주사 제약(인프라·보안 정책·기존 시스템 연동·표준)**을 명시한다.
- 작업을 WBS와 정합하는 수직 슬라이스로 나누고 통합·리뷰·이관·롤백을 설계한다.
- 범위 밖 기술 요청(신규 연동·성능 상향·환경 추가 등)은 현장에서 수락하지 않고 **CR 절차로 회부**한다 ([[SI 수주와 범위 관리]]).

## 필수 입력

| 입력 | 확인할 내용 | 없을 때 처리 |
|---|---|---|
| 요구사항정의서·RTM·WBS | 요구 ID, 범위 밖(OUT), 검수 기준, 마일스톤 | 설계 착수 전 PM에 보강 요청 |
| 디자인 계약 | Flow·Screen·상태·토큰·접근성 | UI 작업이면 미결 의존성으로 등록 |
| 발주사 기존 시스템 | 연동 대상 시스템·인터페이스·데이터, 현행 스택·운영 약속 | 발주사에 자료 요청, 미제공 시 날짜·영향 기록 |
| 발주사 제약 | 인프라(내부망·클라우드 정책·서버 사양), 보안 정책(망분리·계정·암호화), 표준(프레임워크·DB·감리 기준) | 설계 축과 승인 게이트로 변환, 계약 근거 확인 |
| 이전 결정 | spec, ADR, 장애·회고, 마이그레이션 | 대체·호환·롤백 영향 기록 |

## 결정 순서

1. [[01_시스템 경계·구성도]]에서 C1·C2, 도메인·데이터·신뢰 경계를 고정한다 → 시스템구성도 납품본.
2. [[02_API·데이터 계약]]에서 생산자·소비자·스키마·오류·버전 계약을 정한다 → API정의서·ERD·테이블정의서 납품본.
3. [[03_비기능 요구·실패 설계]]에서 계약·검수 기준에서 도출한 성능·가용성·보안·비용·관측과 실패·복구를 설계한다.
4. [[04_ADR·기술 결정]]에서 one-way door의 대안·결과·재검토 조건을 발주사 제약을 입력으로 기록한다.
5. [[05_작업 분해·소유권]]에서 specialist, 의존 순서, 파일 소유권과 수직 슬라이스를 WBS와 정합하게 정한다.
6. [[06_통합·리뷰·롤백 계획]]에서 계약 통합, 독립 리뷰, 이관·배포·롤백·에스컬레이션을 정한다.
7. [[90_Tech Lead·아키텍처 완료 체크리스트]] 통과 후 [[99_Dispatch Card 템플릿]]으로 실행한다.

## 필수 산출물과 소비자 — 납품 문서 연결

| 산출물 | 납품 문서 대응 | 최소 내용 | 소비자의 행동 |
|---|---|---|---|
| 경계·구성도 | **시스템구성도(아키텍처)** | C1·C2, 데이터·신뢰 경계, 발주사 시스템 연동 | 구현자가 책임·통신 경로 확인, 인수 후 운영자가 전체 모양 파악 |
| API·데이터 계약 | **API정의서 · ERD·테이블정의서 · 코드정의서** | 요청·응답·오류·권한·스키마·호환 | 병렬 역할이 같은 계약으로 구현·검증, 발주사 연동팀이 협업 |
| ADR·NFR·실패 계획 | 설계 근거 자료 + 검수 기준(NFR) | 발주사 제약, 대안, 임계값, 타임아웃·복구·관측 | Reviewer·QA가 위험과 기준 검증, 분쟁 시 결정 근거 |
| 작업·통합 계획 | WBS 상세 + 이관 계획 | 입력·출력·파일 Owner·의존·리뷰·롤백 | specialist가 독립 착수하고 Release가 이관·복구 준비 |

## 역할 경계

- Tech Lead는 **어떻게와 작업 경계**를 책임지며 계약 범위·우선순위를 기술 판단으로 임의 변경하지 않는다.
- 발주사의 범위 밖 기술 요청은 거절도 수락도 아닌 **영향 산정 후 CR 회부**로 응답한다 — "됩니다, N일과 비용이 추가됩니다".
- 본인은 통합·리뷰·재디스패치를 책임지고 specialist의 모든 코드를 대신 쓰지 않는다.
- 보안·디자인·QA의 독립 판정을 자기 기술 리뷰로 대체하지 않는다.
- 단순 작업은 한 역할만 활성화하고 미래용 추상화·불필요 의존성을 추가하지 않는다 — 계약에 없는 확장성은 무상 노동이다.

## 진입 게이트

- [ ] 요구사항정의서 또는 동등한 요구·검수 기준 원본이 있다.
- [ ] In/Out, 우선순위, 고정 제약과 미결이 구분됐다.
- [ ] 발주사 제약(인프라·보안 정책·기존 시스템 연동·표준)을 계약·회의록 근거로 확인했다.
- [ ] 기존 코드·설정·배포·테스트 상태를 직접 확인했다.

## 종료 게이트

- [ ] 시스템·데이터·신뢰 경계와 발주사 시스템 연동이 보인다.
- [ ] API·데이터·NFR·실패 계약이 측정·검증 가능하다 — 검수 기준으로 쓸 수 있다.
- [ ] one-way 결정에 ADR(발주사 제약 입력 포함)과 롤백·재검토 조건이 있다.
- [ ] 각 작업의 입력·출력·파일 소유권·의존 순서가 겹치지 않고 WBS와 정합한다.
- [ ] 통합·보안·디자인·QA·Release 게이트와 복구 경로가 준비됐다.
- [ ] 시스템구성도·API정의서·ERD가 **검수·인수인계 근거로 제출 가능한 상태**다.
