# ADR·기술 결정

> 되돌리기 비싼 결정만 기록한다. 단순 구현 선택은 코드 리뷰에 맡긴다. 외주에서 ADR의 입력은 기술 취향이 아니라 **발주사 제약** — 인프라(내부망·클라우드 정책·서버 사양), 보안 정책(망분리·암호화·계정), 기존 시스템 연동, 발주사 표준(프레임워크·DB·감리 기준)이 먼저 고정되고, 그 안에서 대안을 고른다. ADR은 인수인계 시 "왜 이렇게 만들었나"의 답변서이자 분쟁 시 결정 근거다.

## ADR 승격 판정

| 질문 | 답 |
|---|---|
| 데이터·공개 API·보안·배포·서비스 경계를 바꾸는가? | `{예/아니오}` |
| 틀렸을 때 복구 비용·검수·일정 영향이 큰가? | `{값}` |
| 대안 간 실제 트레이드오프가 있는가? | `{값}` |
| 발주사 제약·표준과 충돌 가능성이 있는가? | `{값 — 있으면 무조건 ADR}` |
| 결론 | `ADR 작성 / two-way 결정으로 즉시 실행` |

## ADR 템플릿

| 항목 | 값 |
|---|---|
| ADR ID·제목 | `ADR-{NNN}: {제목}` |
| 상태 | `Proposed / Accepted / Deprecated / Superseded` |
| Owner / Reviewer / Approver | `{값 — 발주사 승인 필요 여부 표시}` |
| 연결 요구·NFR | `{ID}` |
| 결정일·기준 commit | `{날짜 · SHA}` |

### 발주사 제약 입력 (결정 전 고정)

| 제약 | 내용 | 근거(계약·정책·회의록) | 협상 가능 여부 |
|---|---|---|---|
| 인프라 | `{내부망/DMZ·클라우드 허용 범위·서버 사양·가용 자원}` | `{링크·일자}` | `{고정/협의}` |
| 보안 정책 | `{망분리·암호화 표준·계정 발급·반출 절차}` | `{값}` | `{값}` |
| 기존 시스템 연동 | `{연동 대상·인터페이스 방식·사양 제공 상태}` | `{값}` | `{값}` |
| 발주사 표준 | `{지정 프레임워크·DB·감리·산출물 기준}` | `{값}` | `{값}` |
| 운영·유지보수 | `{인수 후 운영 주체의 기술 역량·라이선스 정책}` | `{값}` | `{값}` |

> 제약과 요구가 충돌하면(예: 보안 정책상 요구 기능 구현 불가) 임의로 우회 설계하지 말고 PM에 회부한다 — 범위 재협상 또는 CR 대상이다.

- 해결할 기술 문제: `{한 문장}`
