# PM·PO·BA 완료 체크리스트

## SRS·범위

- [ ] 문제·현업 사용자·AS-IS 업무가 계약·수주 결정과 연결됐다.
- [ ] 모든 요구가 RFP 항목·계약 조항 근거를 갖는다 — 근거 없는 요구는 CR 후보로 분류됐다.
- [ ] 완성 데모(검수) 시나리오가 입력과 관찰 가능한 결과로 적혔다.
- [ ] 포함과 제외(Out of Scope)가 각각 ID·계약 근거를 갖고 계약서 제외 목록과 정합한다.
- [ ] 업무 규칙마다 발주사 측 결정 Owner가 명확하다.

## 요구·완료 조건

- [ ] 모든 요구에 고유 ID·Owner·구분(계약 Must/CR 후보)이 있다.
- [ ] 계약 Must 요구에는 Given-When-Then 수용 기준이 있다.
- [ ] 성능·가용성·보안·데이터 정합·접근성 중 관련 NFR이 임계값과 합의 근거로 작성됐다.
- [ ] 기능·품질·회귀 완료 조건을 실제로 실행할 수 있고 검수 기준으로 발주사와 합의됐다.
- [ ] 사람 판정 항목은 판정자·기준표·수정 라운드 상한이 있다.
- [ ] 요구사항에 구현 방법을 몰래 확정하지 않았다 (발주사 지정 스택 제외).

## WBS·마일스톤

- [ ] WBS가 계약 범위 전체를 덮고 발주사 제공 필요일이 박혔다.
- [ ] 첫 구간이 입력→처리→출력→배포를 관통하고 중간 데모일이 잡혔다.
- [ ] 마일스톤마다 납품 산출물·검수 기준·지불 조건·검수 기간 상한이 있다.
- [ ] 단계 오픈(파일럿→베타→가오픈→오픈) 진입·종료 조건이 있다.
- [ ] 범위 동결일 이후 변경은 CR로만 처리된다는 규칙이 명시됐다.

## 위험·추적

- [ ] 리스크에 신호·완화·발생 시 대응·Owner·기한이 있다.
- [ ] 의존성에 제공자·필요일·수용 형식·대체 행동이 있다.
- [ ] 발주사 제공 사항 표에 필요일·실제 제공일·지연 기록·통지 링크 열이 준비됐다.
- [ ] 외부 계정·데이터·승인 값 자체를 문서에 노출하지 않았다.
- [ ] RTM의 모든 계약 Must·NFR 요구에 설계·테스트·발주사 검수를 채울 경로가 있다.
- [ ] 미결·미수행·조건부·CR 항목이 빈칸으로 숨겨지지 않았다.

## S-skills 인계

- [ ] `.state/pm-brief.md` 첫 줄이 `[HINT:single={hint}]` 형식이다.
- [ ] `## 태스크 목록`, `## 리스크`, `## 완료 조건 (기계 검증 가능)`이 있다.
- [ ] 완료 조건이 원본 요구 ID(SRS)와 연결된다.
- [ ] 단일 역할 힌트는 실제 한 specialist로 끝나는 경우에만 썼다.
- [ ] Tech Lead·QA가 실제 문서 경로와 기준 버전(검수본)을 찾을 수 있다.

- 보완 Owner·기한: `{값}`
- 인계 대상·다음 행동: `{역할 · 행동}`
- Reviewer·Approver·일시: `{값}`
