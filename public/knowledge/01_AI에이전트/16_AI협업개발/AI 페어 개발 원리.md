# AI 페어 개발 원리

> 한 줄 정의
> AI에게 구현을 맡길 때 사람이 지키는 운용 원리. 3축: **명세(입력의 질) · 검증(출력의 판정) · 게이트(비가역의 통제)**. [[AI-DEVELOPMENT-RULES]]가 AI 쪽 규칙이라면, 이 문서는 사람 쪽 운용법이다.

## 해결하는 문제

- AI의 구현 능력은 이미 병목이 아니다. 병목은 **의도 전달의 정밀도**와 **산출물 검증 비용**이다.
- 검증 없는 신뢰는 "그럴듯한 미완성"을 프로덕션에 보낸다. 통제 없는 불신은 AI를 자동완성 수준으로 낭비한다.

## 핵심 원리

### 1. 산출물 품질은 명세 품질에 수렴한다
- 프롬프트 표현을 다듬는 것보다 **완료 조건을 기계 검증 가능하게** 만드는 것이 수익이 크다 → [[요구사항과 완료 조건]].
- 완료 조건이 실행 가능하면 AI는 스스로 루프를 돈다(생성→실행→검증→수정). 조건이 모호하면 모든 반복에 사람이 낀다.
- 태스크 크기 기준: **한 세션에서 검증까지 끝나는 크기**로 자른다. 넘치면 [[우선순위와 스코프]]의 수직 슬라이스로.

### 2. 검증자와 구현자를 분리한다 (Judge 독립성)
- 구현한 컨텍스트가 자기 결과를 판정하면 자기 편향이 낀다 — "내가 이해한 요구사항"에 맞춰 채점한다.
- 판정자에게는 **요구사항 원본 + 실제 산출물**만 준다. 구현자의 자기 평가(요약·완료 주장)는 입력에서 제외한다.
- 1인 운용이라도 최소한 세션을 분리한다: 구현 세션 ≠ 리뷰 세션.

### 3. 비가역 행동은 사람 게이트 뒤에
- 머지·배포·발송·과금·삭제는 AI가 준비까지만, 실행은 사람이 ([[AI-DEVELOPMENT-RULES]] B-8의 운용 측면).
- 게이트를 지키는 것은 의지가 아니라 구조다: 권한 자체를 주지 않거나, 승인 단계를 파이프라인에 배선한다.
- 원칙: **루프를 만들고, 엔지니어로 남는다** — 자동화의 대상은 반복이지 책임이 아니다.

### 4. 신뢰는 곡선이다 — 검증 비용으로 위임 범위를 정한다

| 단계 | 위임 범위 | 검증 방식 |
|------|----------|----------|
| 1 | 테스트 있는 소규모 수정 | diff 전체 읽기 |
| 2 | 기능 단위 (완료 조건 명시) | 완료 조건 실행 + diff 훑기 |
| 3 | 파이프라인 (구현+자체 검증) | 독립 판정자 + 샘플링 검토 |

- 승급 조건: 해당 단계의 검증 통과율이 안정적으로 높을 때. 사고가 나면 한 단계 강등하고 원인을 [[AI-실수패턴]]에 기록한다.

### 5. AI 실패 모드별 구조적 대응 — 지시가 아니라 장치로

| 실패 모드 | 증상 | 구조적 대응 |
|----------|------|------------|
| 과설계 | 요청 밖 추상화·설정화 | 스코프 아웃 명시 + "모든 변경 줄이 요구 문장으로 소급" 리뷰 규칙 |
| 침묵 실패 | 못 한 검증을 한 것처럼 보고 | 산출물에 `미수행: {이유}` 필수 칸 (정직 계약) |
| 맥락 상실 | 긴 세션 뒤 일관성 붕괴 | 상태 파일 외부화 → [[개발 세션 컨텍스트 운용]] |
| 아첨 | 사람 의견에 무조건 동조 | "반박 근거 1개 필수" 형식의 리뷰 프롬프트 |
| 그럴듯한 날조 | 미확인 API를 기억으로 코딩 | 실제 버전 문서 확인 강제 ([[AI-실수패턴]] #3) |

## 안티패턴

- **바이브 코딩의 프로덕션 반입** — 검증 없는 신뢰. 데모와 운영의 구분 붕괴.
- **diff 안 읽는 승인** — 게이트가 형식이 되는 순간 사고는 시간 문제다.
- **무한 대화 태스크** — 한 세션에 목표를 계속 추가. 완료 조건이 계속 밀린다.
- **프롬프트 마법 탐색** — 명세·검증 구조는 그대로 두고 표현만 바꿔 가며 재시도.
